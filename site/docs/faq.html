Perguntas frequentes

Esta é uma ferramenta da Anthropic?

Não. É uma implementação independente do processo de revisão que o time do Claude Code na Anthropic descreveu em How the Claude Code team does code review (Addy Osmani, Morgan Westlee Lunt e Qing Wang, 15 de outubro de 2026). Não tem vínculo nem endosso da Anthropic. Os textos e o código daqui são do próprio repositório.

Quais são as sete camadas?

Verificar antes do PR, revisão por IA em todo PR, revisão de segurança que pode bloquear, checagens automáticas que bloqueiam, aprovação humana proporcional ao risco, fila de merge com flags e release gradual, e detecção rápida com rollback rápido. Nenhuma verificação pega tudo, então as camadas são empilhadas para que os furos não se alinhem.

O motor de segurança usa LLM?

Não. A camada III é Go determinístico: sem modelo, sem chamada de rede, sem chave de API. O mesmo diff sempre gera os mesmos achados e o mesmo código de saída. Os papéis de revisor das camadas I, II e V rodam no agente de código que você já usa.

O que faz um achado aparecer?

Evidência no diff. Todo achado tem um path:line. Um achado sem isso é retido, e um sink cuja origem está fora do diff é reportado como evidência insuficiente, não com um CWE adivinhado.

Quando ele bloqueia um merge?

O motor sai com código 1 quando algum achado tem ação BLOCK, ou seja, severidade HIGH ou CRITICAL. Achados MEDIUM são REVIEW e não mudam o código de saída. O único HIGH que fica em REVIEW é a regra do header do Cloudflare Access, porque a checagem do JWT pode estar fora do diff.

Quais IDs do OWASP ele imprime?

Só identificadores oficiais, de um catálogo fixo: OWASP Top 10:2021, OWASP API Security Top 10:2023 e ASVS 5.0. Achados de prompt injection levam ASI01:2026 e AST05.

Um comentário no diff consegue convencê-lo a não bloquear?

Não. O diff é tratado como dado não confiável. Um texto com cara de instrução é, ele mesmo, um achado (CWE-1427, BLOCK) e não cancela nenhum outro BLOCK.

Quais linguagens ele cobre?

JavaScript e TypeScript, workflows do GitHub Actions e manifestos e lockfiles de pacotes JavaScript em todas as regras. As regras web (XSS, CORS, SSRF, AuthZ/IDOR) e as de injection também cobrem Python (Flask, Django, FastAPI), Go (net/http, chi, gin), Java (Spring, Servlet, JSP, Thymeleaf) e PHP (PHP puro, Laravel, Blade, Twig). O motor é escrito em Go e precisa do Go 1.27 ou mais recente.

Dá para rodar no CI?

Sim. A GitHub Action revisa todo pull request, escreve uma tabela de achados no resumo do job, envia o SARIF ao Code Scanning e falha o job em BLOCK. O motor também escreve JSON (schemaVersion 1). Em qualquer outro CI, rode review --git --from <base> --to HEAD e deixe o código de saída 1 falhar o job.

Existe um passe de LLM em cima do motor?

Sim, opcional, e ele só pode descartar ou rebaixar achados, nunca adicionar. O modelo segue o papel reviewers/triage.md e escreve um arquivo de veredictos; review --triage veredictos.json aplica e garante em código que nenhum achado é criado e nenhuma severidade sobe. Achados de segredo e de prompt injection são imunes, e um veredicto inválido rejeita o arquivo inteiro com código 2 e sem relatório. Cada veredicto aplicado aparece no relatório em texto, JSON e SARIF.

É uma auditoria de segurança completa?

Não. É uma revisão rápida de pull request para um conjunto definido de classes. Não é SCA, nem auditoria ASVS, nem teste de intrusão. Use ao lado de SAST e SCA, não no lugar deles.
