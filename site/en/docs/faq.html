Frequently asked questions

Is this an Anthropic tool?

No. It is an independent implementation of the review process the Claude Code team at Anthropic described in How the Claude Code team does code review (Addy Osmani, Morgan Westlee Lunt and Qing Wang, 15 October 2026). It is not affiliated with or endorsed by Anthropic. Wording and code here are this repo’s own.

What are the seven layers?

Verify before the PR, AI review on every PR, security review that can block, blocking automated checks, human approval scaled by risk, a merge queue with flags and a gradual release, and fast detection with fast rollback. No single check catches everything, so the layers are stacked so their holes do not line up.

Does the security engine use an LLM?

No. Layer III is deterministic Go: no model, no network call, no API key. The same diff always produces the same findings and the same exit code. The reviewer roles of layers I, II and V run in the coding agent you already use.

What makes a finding appear?

Evidence in the diff. Every finding has a path:line. A finding without one is withheld, and a sink whose source is outside the diff is reported as insufficient evidence, not as a guessed CWE.

When does it block a merge?

The engine exits with code 1 when any finding has action BLOCK, which means severity HIGH or CRITICAL. MEDIUM findings are REVIEW and do not change the exit code. The one HIGH that stays REVIEW is the Cloudflare Access header rule, because the JWT check may live outside the diff.

Which OWASP IDs does it print?

Official identifiers only, from a fixed catalog: OWASP Top 10:2021, OWASP API Security Top 10:2023 and ASVS 5.0. Prompt-injection findings carry ASI01:2026 and AST05.

Can a comment in the diff talk it out of blocking?

No. The diff is treated as untrusted data. Instruction-shaped text is itself a finding (CWE-1427, BLOCK) and does not cancel any other BLOCK.

Which languages does it cover?

JavaScript and TypeScript, GitHub Actions workflows and JavaScript package manifests and lockfiles for every rule. The web rules (XSS, CORS, SSRF, AuthZ/IDOR) and the injection rules also cover Python (Flask, Django, FastAPI), Go (net/http, chi, gin), Java (Spring, Servlet, JSP, Thymeleaf) and PHP (plain PHP, Laravel, Blade, Twig). The engine itself is written in Go and needs Go 1.27 or later.

Can I run it in CI?

Yes. The GitHub Action reviews every pull request, writes a findings table to the job summary, uploads SARIF to Code Scanning and fails the job on BLOCK. The engine also writes JSON (schemaVersion 1). In any other CI, run review --git --from <base> --to HEAD and let exit code 1 fail the job.

Is there an LLM pass on top of the engine?

Yes, optional, and it can only drop or downgrade findings, never add them. The model follows the reviewers/triage.md role and writes a verdicts file; review --triage verdicts.json applies it and enforces in code that no finding is created and no severity goes up. Secret and prompt-injection findings are immune, and one invalid verdict rejects the whole file with exit code 2 and no report. Every applied verdict shows in the text, JSON and SARIF reports.

Is this a full security audit?

No. It is a pull-request smoke review for a defined set of classes. It is not SCA, not an ASVS audit and not a penetration test. Use it next to SAST and SCA, not instead of them.
